# 企画書: Flex Railway Map を Flutter でアプリにする（2026-11）

関連: 仕様書 `docs/app/flutter-app-spec.md` / UI の見直し `docs/app/ui-review-2026-11.md`

## 1. ひとことで

**地図と経路は Flutter で作り直し、記事・ガイドは今の Web をアプリの中で開く。**
Web とアプリで路線データ・駅データ・翻訳・デザインの値を共有し、同じものを2回書かない。

## 2. なぜアプリにするか

今の Web 版で「できない・弱い」ことを、アプリなら解決できる。

| 場面 | Web 版の今 | アプリでできること |
|---|---|---|
| 乗っている間の到着アラート | iPhone の Safari では、ホーム画面に追加しないと通知が出ない。画面を消すと位置が取れない | OS のローカル通知。許可があれば画面を消していても降りる駅の手前で知らせる |
| 地下・電波の弱い所 | 毎回読み込む。地図タイルも外部から取る | 路線・駅・時刻表を端末に入れておき、電波が無くても経路が引ける |
| すぐ開く | ブラウザ → ブックマーク → 読み込み | ホーム画面のアイコン、よく使う経路のウィジェット |
| 見つけてもらう | 検索（SEO）だけ | App Store / Google Play の検索 |
| 操作のしやすさ | 押せるものがすべて 44px 未満、設定が1か所に積み上がっている（UI の見直し参照） | 地図を全画面にして、下から出るシートと設定画面に整理し直す |

このサービスの考え方（「推薦の経路に頼らず、出発駅と到着駅に関係する路線だけの路線図で自分で判断できる」）は変えない。
遅延・運休のときに開くアプリなので、**すぐ開けること・電波が無くても動くこと**が特に効く。

## 3. 誰が使うか

- 普段の通勤・通学で、遅延時に別の経路を自分で考えたい人（首都圏が中心。全国約490路線・約6,000駅を収録）
- 旅行で来た人（英語・中国語・韓国語の4言語）
- 住む場所を探している人（駅ごとの施設数などのヒートマップ）

## 4. 作り方の比較

| 方式 | 中身 | 工数 | 審査で落ちる心配 | 使い心地 | 保守 |
|---|---|---|---|---|---|
| A. Web を包むだけ | Flutter の WebView で今のサイトを全画面で開く | 小（1〜2週間） | **大**。App Store の審査基準 4.2（最低限の機能）で「Web サイトを包んだだけのアプリ」は落ちやすい | Web 版と同じ（押しにくさも同じ） | 楽 |
| **B. ハイブリッド（推奨）** | 地図・駅検索・経路・時刻表・設定は Flutter で作る。記事・ガイド・このサイトについては WebView | 中（MVP 8〜12週間） | 小。アプリならではの機能（オフライン・通知・ウィジェット）がある | アプリとして作り直せる | データは共有。経路探索は Dart に移すので「同じ答えを出すか」のテストが要る |
| C. すべて Flutter | 記事・ガイドまで Flutter で作り直す | 大 | 小 | 最もよい | 記事を2か所で持つことになり重い |
| （参考）PWA / TWA | 今の PWA をそのまま使う / Android は TWA でストアに出す | 小 | iOS のストアには出せない | Web 版と同じ | 楽 |

**B を推す理由**
- 審査を通るには「Web を包んだだけではない」中身が要る。B なら地図・経路・通知・オフラインがアプリの中身になる
- 記事は SEO の入口として Web で育てているので、アプリで作り直す意味が薄い
- データ（路線・駅・時刻表・翻訳）は今のリポジトリが一次情報。アプリ用に JSON を書き出して共有すれば、二重管理にならない

## 5. 最初に作る範囲（MVP）

**作る**
1. 地図（路線と駅。経路に関係する路線だけを出す、が中心）
2. 駅検索（漢字・かな・英語）、出発・到着・入れ替え・現在地から
3. 経路の候補（所要時間・乗換回数・使う路線）と、乗り換えの詳細
4. 駅を押したときの下部シート（ここから / ここまで / 路線ごとの時刻表）
5. 路線の表示切り替え（検索つき）
6. 設定（地図の見た目・言語・テーマ）
7. 4言語（日本語・英語・中国語・韓国語）、ダークテーマ
8. 記事・ガイドは WebView で開く

**次に作る**
- 到着アラート（ローカル通知・バックグラウンドの位置情報）
- よく使う経路の保存とホーム画面ウィジェット
- 地図の背景をオフラインで持つ
- ヒートマップ（駅ごとの施設数など）、簡略図

**当面作らない**
- 立体表示（three.js で作った地形の 3D）。Flutter で作り直す費用が大きく、使う人が少ない
- 列車の現在位置のデモ表示

## 6. お金の話

**かかるもの**（2026-11 時点。金額は各社の案内で要確認）
- Apple Developer Program: 年 99 米ドル（日本の価格は Apple の案内による）
- Google Play の開発者登録: 1回 25 米ドル
- iOS のビルドには Mac（Xcode）が要る。手元に無ければ macOS で動く CI（GitHub Actions の macOS 実行環境・Codemagic など）
- 地図の背景タイル: 今の Web 版が使っている OpenStreetMap の標準タイルはアプリには使えない（仕様書の 4.3）。
  無料枠のある提供元（MapTiler・Stadia Maps など）か、自前で置く（Protomaps の PMTiles）

**入るもの**
- 広告は **AdMob**（アプリ用の Google 広告）。AdSense はアプリの画面には使えない
- Web 版で決めた方針を引き継ぐ: **こちらで決めた位置にだけ出す。全画面広告・アプリ起動時の広告は使わない**
- 広告なしの有料版（買い切り or 月額）は、使う人が増えてから考える

## 7. 進め方と目安

1人 + AI で進める前提の目安。

| 段階 | やること | 目安 |
|---|---|---|
| 0. 準備 | 路線・駅・時刻表・翻訳・デザインの値を JSON に書き出す仕組み、経路探索の「正解データ」 | 1〜2週間 |
| 1. MVP | 5章の「作る」 | 6〜8週間 |
| 2. 出す準備 | アイコン・ストアの画像と説明（4言語）、プライバシーポリシーの更新、AdMob と同意画面、計測、審査 | 2〜3週間 |
| 3. アプリならでは | 到着アラート、ウィジェット、オフライン地図 | 4〜6週間 |

並行して Web 版の UI も直す（UI の見直しの A・B・C）。アプリの画面構成と同じ考え方にそろえると、両方で同じ説明ができる。

## 8. 心配なことと対策

| 心配 | 対策 |
|---|---|
| 経路探索を Dart に移すと、Web と答えがずれる | TypeScript 版で数百組の「出発→到着」の正解を JSON に書き出し、Dart 版が同じ答えを出すかを CI で毎回確かめる |
| 路線データを直すたびにアプリを出し直すのは重い | データはアプリに同梱しつつ、版番号つきの JSON を Web から取り直せるようにする（審査なしで更新できる） |
| 地図タイルの費用が増える | 無料枠の範囲を測る。超えそうなら自前の PMTiles に切り替える |
| 審査で落ちる（4.2 最低限の機能） | MVP の時点でオフライン経路・駅検索・時刻表を Flutter で持つ。審査メモにアプリだけの機能を書く |
| 同意画面の順番で落ちる（iOS の ATT） | Google の同意画面（UMP）→ OS の追跡許可（ATT）の順にする。自作の確認画面を挟まない |
| 1人で Web とアプリの両方を見る負担 | データ・翻訳・デザインの値を共有し、書き出しを自動にする。アプリ側は画面だけを書く |

## 9. 決めてほしいこと

1. 方式は B（ハイブリッド）でよいか
2. 最初は iOS と Android を同時に出すか、片方から出すか（Android が先なら Mac が無くても進められる）
3. Apple / Google の開発者登録を誰の名前でするか（個人 / 屋号）
4. 地図の背景タイルの提供元（費用と見た目で選ぶ。Web 版も同じものに替えると、Web 版の OpenStreetMap 標準タイルの問題も同時に片づく）
5. 有料版（広告なし）を最初から用意するか
